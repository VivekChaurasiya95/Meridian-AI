**Document:** `DATABASE.md`\
**Product:** Meridian --- Clarity for complex engineering\
**Status:** Proposed MVP schema\
**Primary database:** PostgreSQL\
**Schema version:** `001_initial`\
**Last updated:** 2026-10-28

------------------------------------------------------------------------

## 1. Purpose

This document defines Meridian's relational data model for users,
workspaces, repositories, investigations, evidence, hypotheses,
regression tests, patch proposals, verification runs, and audit history.

It is intended to be the implementation contract for database migrations
and repository-level data access. The schema should support a complete
investigation lifecycle while keeping the model's claims separate from
facts established by deterministic tools.

### 1.1 Design goals

-   Preserve investigation history and stage outcomes.
-   Keep evidence artifacts traceable to the project, investigation, and
    tool run that produced them.
-   Store model-generated hypotheses separately from observed evidence.
-   Track proposed patches and approval decisions without treating a
    proposal as verified.
-   Record actual verification commands, exit codes, test results, and
    limitations.
-   Support workspace-level authorization and tenant isolation.
-   Avoid storing large logs, screenshots, traces, ZIP files, or patch
    blobs directly in PostgreSQL.
-   Make state transitions and security-sensitive actions auditable.

### 1.2 Database is not the source of truth for execution

PostgreSQL stores records of what the runner and verification engine
reported. It does **not** make a run successful merely because a row
says `completed`.

The application must derive verification status from persisted,
validated runner results. Never set a patch to "verified" just because
the model claims it is fixed, a patch was generated, or a test was
suggested.

## 2. Database conventions

### 2.1 Naming and identifiers

-   Use `snake_case` for schemas, tables, columns, indexes, constraints,
    and enum labels.
-   Use UUID primary keys, generated by the application or PostgreSQL.
-   Use `timestamptz` for all persisted timestamps.
-   Store timestamps in UTC; convert for display in the client.
-   Use `text` for variable-length strings unless a real constraint
    justifies a bounded type.
-   Use `jsonb` for small, structured, versioned metadata---not as a
    substitute for relational modeling.
-   Store SHA-256 digests as 64-character lowercase hexadecimal strings.
-   Use `bytea` only for small binary values where external object
    storage is inappropriate.
-   Add `created_at` and, where useful, `updated_at` consistently.
-   Use soft deletion sparingly. For privacy-driven deletion, define a
    real deletion workflow instead of relying on `deleted_at` alone.

### 2.2 Extensions

Initial migration:

``` sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
```

Use `gen_random_uuid()` for defaults if UUIDs are generated in
PostgreSQL. If using a managed PostgreSQL service that restricts
extensions, confirm availability before migration.

### 2.3 Suggested schemas

For the MVP, use one PostgreSQL schema named `public` with clear table
ownership and strict access patterns. Separate schemas such as `audit`
or `internal` can be introduced later if access requirements justify
them.

### 2.4 Common timestamp pattern

``` sql
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()
```

`updated_at` does not update automatically without a trigger or explicit
application update. Implement one consistent strategy. Do not rely on
application developers remembering this inconsistently.

### 2.5 Enumerations

PostgreSQL enums can make invalid states harder to represent, but they
can be awkward to evolve. For workflow states that may change during
early product development, prefer `text` plus `CHECK` constraints or
lookup tables. The SQL below uses text/check constraints for lifecycle
states.

  -----------------------------------------------------------------------

                                      confidence, status, and supporting

                                      for a verification run

  `activity_events`                   User-visible timeline events within
                                      an investigation

                                      events for traceability

  `repository_snapshots`              Immutable references to the

The first twelve product tables align with the PRD.
`repository_snapshots`, `tool_runs`, and `idempotency_keys` are added to
make the MVP's execution and retry semantics safer and more traceable.

## 5. Core data model

### 5.1 `users`

Stores the application-level user record. Authentication credentials and
provider secrets remain with the identity provider.

  -----------------------------------------------------------------------------
  Column               Type              Rules             Description
  -------------------- ----------------- ----------------- --------------------
  `id`                 `uuid`            PK                Internal user ID

  `auth_provider`      `text`            NOT NULL          Provider identifier,
                                                           e.g. `firebase`

  `provider_subject`   `text`            NOT NULL          Stable user ID from
                                                           provider; not an
                                                           access token

  `email`              `text`            NULL allowed      Email if supplied
                                                           and permitted

  `display_name`       `text`            NULL allowed      Display name

  `avatar_url`         `text`            NULL allowed      Optional provider
                                                           image URL

  `status`             `text`            NOT NULL, checked `active`,
                                                           `disabled`,
                                                           `deletion_pending`

  `created_at`         `timestamptz`     NOT NULL          Creation time

  `updated_at`         `timestamptz`     NOT NULL          Last update
  -----------------------------------------------------------------------------

Unique key: (`auth_provider`, `provider_subject`). Email is not the
identity key; it may change or be absent.

### 5.2 `workspaces`

A workspace is the authorization boundary for projects and
investigations.

  Column         Type            Rules             Description
  -------------- --------------- ----------------- ------------------------------
  `id`           `uuid`          PK                Workspace ID
  `name`         `text`          NOT NULL          Display name
  `slug`         `text`          NOT NULL          Human-readable workspace key
  `created_by`   `uuid`          FK → `users.id`   Creator
  `created_at`   `timestamptz`   NOT NULL          Creation time
  `updated_at`   `timestamptz`   NOT NULL          Last update

Slug uniqueness should be scoped according to routing needs. The initial
schema uses a globally unique slug for simpler URLs. If private
workspace URLs do not need global uniqueness, change this before
migration.

### 5.3 `workspace_members`

Defines workspace roles.

  -----------------------------------------------------------------------
  Column            Type              Rules             Description
  ----------------- ----------------- ----------------- -----------------
  `workspace_id`    `uuid`            PK part, FK       Workspace

  `user_id`         `uuid`            PK part, FK       Member

  `role`            `text`            NOT NULL, checked `owner`, `admin`,
                                                        `developer`,
                                                        `viewer`

  `joined_at`       `timestamptz`     NOT NULL          Membership start

  `invited_by`      `uuid`            FK → `users.id`,  Inviter
                                      nullable          
  -----------------------------------------------------------------------

A workspace must retain at least one owner. A row-level `CHECK` cannot
enforce "at least one owner" across multiple rows. Enforce
owner-transfer/removal rules in a transaction or with a carefully
designed deferred trigger.

### 5.4 `projects`

Represents a codebase known to Meridian.

  --------------------------------------------------------------------------------------------
  Column                       Type              Rules             Description
  ---------------------------- ----------------- ----------------- ---------------------------
  `id`                         `uuid`            PK                Project ID

  `workspace_id`               `uuid`            FK →              Tenant
                                                 `workspaces.id`   

  `created_by`                 `uuid`            FK → `users.id`   Creator

  `name`                       `text`            NOT NULL          Project display name

  `description`                `text`            NULL              Optional description

  `source_type`                `text`            NOT NULL, checked `git_provider`,
                                                                   `uploaded_archive`

  `repository_url`             `text`            NULL              Canonical remote URL; never
                                                                   include credentials

  `provider_installation_id`   `text`            NULL              External installation
                                                                   reference, if applicable

  `default_branch`             `text`            NULL              Default branch

  `status`                     `text`            NOT NULL, checked `active`, `archived`,
                                                                   `setup_failed`

  `runtime_profile`            `jsonb`           NOT NULL default  Allowlisted
                                                 `{}`              framework/package-manager
                                                                   profile

  `created_at`                 `timestamptz`     NOT NULL          Creation time

  `updated_at`                 `timestamptz`     NOT NULL          Last update
  --------------------------------------------------------------------------------------------

Do not store repository access tokens or credentials in
`repository_url`, `runtime_profile`, or any JSON metadata. Store
credentials in a secrets manager or provider installation, and persist
only a reference if needed.

### 5.5 `repository_snapshots`

Pins the exact repository state inspected by an investigation.

  --------------------------------------------------------------------------
  Column            Type              Rules             Description
  ----------------- ----------------- ----------------- --------------------
  `id`              `uuid`            PK                Snapshot ID

  `project_id`      `uuid`            FK →              Project
                                      `projects.id`     

  `commit_sha`      `text`            NULL              Commit SHA, if
                                                        source is Git

  `tree_digest`     `text`            NOT NULL          SHA-256 digest of
                                                        normalized source
                                                        tree

  `branch_name`     `text`            NULL              Observed branch

  `source_ref`      `text`            NULL              Non-secret source
                                                        revision/reference

  `manifest`        `jsonb`           NOT NULL default  Detected files,
                                      `{}`              language, package
                                                        manager, framework
                                                        versions

  `created_at`      `timestamptz`     NOT NULL          Snapshot time
  --------------------------------------------------------------------------

Store an immutable snapshot record. Do not overwrite a snapshot to
represent a later commit. `manifest` must exclude secrets and
unnecessary source contents.

### 5.6 `investigations`

The primary aggregate for one debugging session.

  -------------------------------------------------------------------------------------------
  Column                     Type              Rules                        Description
  -------------------------- ----------------- ---------------------------- -----------------
  `id`                       `uuid`            PK                           Investigation ID

  `project_id`               `uuid`            FK → `projects.id`           Target project

  `created_by`               `uuid`            FK → `users.id`              Initiating user

  `repository_snapshot_id`   `uuid`            FK →                         Pinned source
                                               `repository_snapshots.id`,   snapshot
                                               nullable initially           

  `title`                    `text`            NOT NULL                     Short bug title

  `bug_report`               `text`            NOT NULL                     User-provided
                                                                            report

  `status`                   `text`            NOT NULL, checked            Lifecycle status

  `current_stage`            `text`            NULL                         Current stage key

  `severity`                 `text`            NOT NULL, checked            `low`, `medium`,
                                                                            `high`,
                                                                            `critical`,
                                                                            `unspecified`

  `result_summary`           `text`            NULL                         User-facing final
                                                                            summary

  `started_at`               `timestamptz`     NULL                         First execution
                                                                            start

  `completed_at`             `timestamptz`     NULL                         Terminal time

  `cancelled_at`             `timestamptz`     NULL                         Cancellation time

  `created_at`               `timestamptz`     NOT NULL                     Creation time

  `updated_at`               `timestamptz`     NOT NULL                     Last update
  -------------------------------------------------------------------------------------------

Suggested statuses: `queued`, `running`, `awaiting_approval`,
`completed`, `failed`, `blocked`, `inconclusive`, `cancelled`.

A `completed` investigation means the workflow reached a valid terminal
outcome; it does not automatically mean the bug was fixed. Store
fix/verification outcome in explicit fields or linked patch and
verification records.

### 5.7 `investigation_stages`

Stores each stage attempt, including retries.

  -------------------------------------------------------------------------------
  Column               Type              Rules                 Description
  -------------------- ----------------- --------------------- ------------------
  `id`                 `uuid`            PK                    Stage execution ID

  `investigation_id`   `uuid`            FK →                  Parent
                                         `investigations.id`   

  `stage_key`          `text`            NOT NULL              Stable stage
                                                               identifier

  `attempt_number`     `integer`         NOT NULL, \> 0        Attempt count

  `status`             `text`            NOT NULL, checked     `pending`,
                                                               `running`,
                                                               `completed`,
                                                               `failed`,
                                                               `blocked`,
                                                               `skipped`,
                                                               `inconclusive`,
                                                               `cancelled`

  `input_summary`      `jsonb`           NOT NULL default `{}` Small, redacted
                                                               input metadata

  `output_summary`     `jsonb`           NOT NULL default `{}` Small, validated
                                                               output metadata

  `error_code`         `text`            NULL                  Stable
                                                               machine-readable
                                                               error

  `error_message`      `text`            NULL                  Sanitized message;
                                                               no secrets

  `started_at`         `timestamptz`     NULL                  Start

  `finished_at`        `timestamptz`     NULL                  Finish

  `created_at`         `timestamptz`     NOT NULL              Row creation
  -------------------------------------------------------------------------------

Unique key: (`investigation_id`, `stage_key`, `attempt_number`). Do not
persist chain-of-thought or hidden reasoning. Store concise conclusions,
tool evidence, and user-visible rationale only.

### 5.8 `evidence_artifacts`

Stores metadata for evidence whose bytes live in private object storage.

  --------------------------------------------------------------------------------------
  Column               Type              Rules                 Description
  -------------------- ----------------- --------------------- -------------------------
  `id`                 `uuid`            PK                    Evidence ID

  `project_id`         `uuid`            FK → `projects.id`    Project

  `investigation_id`   `uuid`            FK →                  Investigation
                                         `investigations.id`   

  `tool_run_id`        `uuid`            FK → `tool_runs.id`,  Producing tool run
                                         nullable              

  `kind`               `text`            NOT NULL, checked     `log`, `screenshot`,
                                                               `trace`, `video`,
                                                               `source_excerpt`,
                                                               `test_output`,
                                                               `build_output`,
                                                               `network_summary`,
                                                               `report`, `other`

  `storage_key`        `text`            NOT NULL              Opaque object key, never
                                                               a public URL

  `mime_type`          `text`            NOT NULL              Detected MIME type

  `byte_size`          `bigint`          NOT NULL, \>= 0       Object size

  `sha256`             `text`            NOT NULL              Content digest

  `redaction_status`   `text`            NOT NULL, checked     `pending`, `redacted`,
                                                               `not_required`, `failed`

  `visibility`         `text`            NOT NULL, checked     `workspace`,
                                                               `investigation_private`

  `metadata`           `jsonb`           NOT NULL default `{}` Non-sensitive structured
                                                               details

  `captured_at`        `timestamptz`     NULL                  Evidence time

  `created_at`         `timestamptz`     NOT NULL              Record creation
  --------------------------------------------------------------------------------------

The object-storage bucket must be private. Authorize every download and
issue short-lived signed URLs only after checking workspace membership.
Validate the actual file type and size. Redact secrets and personal data
before exposure. Never trust the client-provided MIME type or digest.

                                           nullable

                                                                        `succeeded`,
                                                                        `failed`,

                                                                        validated
                                                                        arguments

  `result_summary`       `jsonb`           NOT NULL default `{}`        Validated concise
                                                                        result

  `finished_at`          `timestamptz`     NULL                         Finish

  `created_at`           `timestamptz`     NOT NULL                     Record creation
  ---------------------------------------------------------------------------------------

Never store secret environment variables, full credential-bearing
command strings, raw tokens, or unredacted sensitive output in
summaries.

### 6.1 Important migration review notes

Before applying this migration:

1.  **Workspace membership bootstrap:** Create the workspace and its
    owner membership in one transaction.
2.  **Cross-entity consistency:** The schema has several IDs that must
    belong to the same project/investigation/workspace. Enforce these
    relationships in service-layer validation or add composite foreign
    keys in a later hardening migration. A plain FK validates existence,
    not tenant/project consistency.
3.  **Terminal timestamps:** Set `completed_at` on all terminal
    investigation outcomes, including failed/blocked/inconclusive; or
    adjust the constraint and lifecycle logic together. For
    cancellations, set `cancelled_at` and preferably `completed_at` as
    well for analytics.
4.  **Object storage:** PostgreSQL deletion does not automatically
    remove referenced object bytes. Use an asynchronous deletion/outbox
    workflow and verify deletion.
5.  **Patch approvals:** Approval must bind to `diff_sha256` and
    `base_snapshot_id`. If either changes, clear approval and require
    re-approval.
6.  **Verification integrity:** Only the trusted verification service
    may set a run to `passed`; require at least one executed required
    check and enforce policy in application logic or a trigger.
7.  **Data minimization:** Review every JSON field and log summary for
    credentials, cookies, personal data, and repository secrets.
8.  **Database version:** Confirm the target PostgreSQL version supports
    the selected features and test the migration against an empty
    database in CI.

## 7. Indexing strategy

Index the paths used by the UI and worker queues first. Avoid adding
speculative indexes that slow writes without improving measured queries.

### 7.1 Required access paths

-   Workspace dashboard: `projects(workspace_id, created_at DESC)`.
-   Project investigations:
    `investigations(project_id, created_at DESC)`.
-   Investigation detail: stage attempts, evidence, hypotheses, patches,
    verification runs, and activity ordered by creation time.
-   Worker queue: queued investigations and queued tool/verification
    runs.
-   Audit history: workspace and timestamp, plus resource type/ID.
-   Cleanup: idempotency expiration and object deletion tasks.

### 7.2 Optional partial indexes

If worker polling is implemented using PostgreSQL, consider partial
indexes:

``` sql
CREATE INDEX idx_investigations_queued
ON investigations(created_at)
WHERE status = 'queued';

CREATE INDEX idx_tool_runs_queued
ON tool_runs(created_at)
WHERE status = 'queued';

CREATE INDEX idx_verification_runs_queued
ON verification_runs(created_at)
WHERE status = 'queued';
```

Use `FOR UPDATE SKIP LOCKED` for queue claiming if PostgreSQL is the
queue coordinator. For larger workloads, use a dedicated queue system
while keeping PostgreSQL as the durable source of record.

### 7.3 JSONB indexes

Do not add a GIN index to every JSONB column. Add one only for
demonstrated queries against metadata keys. Prefer typed columns for
frequently filtered/sorted fields.

## 8. Tenant isolation and authorization

Every API operation must first resolve the authenticated user and verify
access to the relevant workspace. Do not rely on a client-supplied
`workspace_id`, `project_id`, or `investigation_id` alone.

### 8.1 Recommended authorization rules

  ---------------------------------------------------------------------------------------
  Role                  View          Create               Edit      Approve       Manage
                               investigation   project/settings        patch      members
  ------------- ------------ --------------- ------------------ ------------ ------------
  `owner`                Yes             Yes                Yes          Yes          Yes

  `admin`                Yes             Yes                Yes          Yes  Yes, except
                                                                                ownership
                                                                                 transfer
                                                                                    rules

  `developer`            Yes             Yes            Limited Yes, subject           No
                                                                  to project 
                                                                      policy 

  `viewer`               Yes              No                 No           No           No
  ---------------------------------------------------------------------------------------

The product may narrow permissions further. Patch approval should be a
distinct authorization check even if developers can normally create
patches.

### 8.2 Query scoping

Preferred pattern: begin with workspace membership, then join to the
requested resource through its project/workspace relationship. Avoid
fetching a row by UUID and only later checking whether the caller can
access it.

### 8.3 PostgreSQL Row-Level Security (RLS)

RLS can provide defense in depth, but only if the application sets the
authenticated user context safely per transaction and prevents
connection-pool context leakage. If adopted:

-   Enable RLS on tenant-owned tables.
-   Use transaction-local settings
    (e.g. `SET LOCAL app.user_id = '...'`) only after verifying the
    authenticated identity.
-   Ensure every pooled connection clears transaction state correctly.
-   Test cross-tenant access attempts.
-   Keep service-worker permissions separate from end-user permissions.
-   Do not assume RLS replaces application authorization or
    object-storage authorization.

For the initial MVP, application-level authorization is mandatory. RLS
is recommended before multi-tenant production launch.

## 9. Data lifecycle, privacy, and retention

### 9.1 Retention policy

Define configurable retention windows before public launch. A reasonable
initial policy proposal:

-   Investigation metadata: retain until user/workspace deletion or
    explicit retention policy.
-   Raw execution logs and browser traces: short retention, such as
    14--30 days, unless pinned by the user.
-   Screenshots and generated reports: retain while the investigation is
    retained, subject to workspace policy.
-   Temporary uploads and isolated workspaces: delete promptly after
    processing or expiry.
-   Idempotency keys: expire after a short retry window, such as 24--72
    hours.
-   Security audit events: retain for a defined operational/security
    period and restrict access.

These are proposed defaults, not legal advice. Expose the final
retention policy clearly to users.

### 9.2 Deletion workflow

Deletion should be asynchronous and idempotent:

1.  Authorize the requester and record the deletion request.
2.  Mark the resource `deletion_pending` or write a deletion job.
3.  Stop queued/running jobs and revoke temporary credentials.
4.  Delete private object-storage blobs and temporary workspaces.
5.  Delete or anonymize relational records according to retention
    requirements.
6.  Verify deletion and record a minimal audit event that does not
    retain deleted content.
7.  Retry failed object deletions and alert on persistent failures.

### 9.3 Sensitive content

Bug reports, source excerpts, logs, traces, screenshots, and test
outputs can contain credentials, customer data, or proprietary code.
Apply:

-   Redaction before rendering or sharing artifacts.
-   Private object storage and short-lived signed URLs.
-   Encryption in transit and at rest.
-   Least-privilege database and worker credentials.
-   Strict log scrubbing and bounded artifact sizes.
-   Clear user-facing data handling and retention controls.

## 10. Transaction boundaries and consistency

### 10.1 Create an investigation

Within one transaction:

1.  Verify the user has project access.
2.  Validate project status and the submitted bug report.
3.  Insert the investigation in `queued` state.
4.  Insert an `investigation.created` activity event.
5.  Insert an audit event if policy requires it.
6.  Persist an outbox/queue record, or publish a queue message only
    after commit.

Avoid the dual-write failure where the database commits but the job
message is lost. Prefer a transactional outbox if a separate queue is
used.

### 10.2 Record stage completion

Within a transaction:

1.  Update the stage attempt with a terminal status and sanitized output
    summary.
2.  Persist artifact metadata for any evidence produced.
3.  Persist hypotheses or verification results linked to that stage.
4.  Insert activity events.
5.  Advance the investigation state only if the current state and stage
    result permit it.

### 10.3 Approve a patch

Within a transaction:

1.  Verify membership and patch-approval permission.
2.  Lock the patch row.
3.  Verify status is `awaiting_approval` and approval is pending.
4.  Confirm the current diff digest equals the digest shown to the
    approver.
5.  Confirm the base snapshot has not become stale under the project's
    policy.
6.  Store approver, decision, note, and timestamp.
7.  Write activity and audit events.
8.  Enqueue application only after the transaction commits.

If the digest or base snapshot changed, reject the approval attempt and
require a new patch review.

### 10.4 Complete verification

Persist the run, check results, and linked output artifacts. The
verification service computes the final status using a deterministic
policy. The UI should show passed, failed, blocked, timed out, or
inconclusive distinctly.

## 11. State and data integrity rules

These rules are part of the application contract even where SQL cannot
conveniently enforce them:

1.  A hypothesis is never evidence; it is a claim linked to evidence.
2.  A patch proposal is not a verified fix.
3.  A suggested test is not an executed test.
4.  A missing check is not a passing check.
5.  A timed-out or blocked run is not a failed test unless the product
    explicitly classifies it that way; preserve the exact outcome.
6.  Every patch approval binds to an immutable diff digest and base
    snapshot.
7.  Every verification run binds to an exact repository snapshot and,
    when applicable, patch.
8.  Tool arguments are validated against an allowlist before execution.
9.  All user-visible artifacts are checked for authorization and
    redaction state.
10. Every stage retry receives a new `attempt_number`; previous attempts
    are preserved.
11. Never store hidden chain-of-thought. Store concise conclusions and
    evidence references.
12. Never store secrets in JSON summaries, activity events, or audit
    metadata.

## 12. Recommended implementation phases

### Phase 1 --- Essential MVP tables

Implement in this order:

1.  `users`
2.  `workspaces`
3.  `workspace_members`
4.  `projects`
5.  `repository_snapshots`
6.  `investigations`
7.  `investigation_stages`
8.  `tool_runs`
9.  `evidence_artifacts`
10. `hypotheses` and `hypothesis_evidence`
11. `regression_tests`
12. `patches`
13. `verification_runs` and `verification_checks`
14. `activity_events` and `audit_events`
15. `idempotency_keys`

Create each table through versioned migrations; do not create or mutate
production schema automatically at application startup.

### Phase 2 --- Hardening

-   Add transactionally enforced owner-membership rules.
-   Add composite foreign keys or equivalent service constraints for
    project/investigation consistency.
-   Introduce an outbox table if using an external queue.
-   Add object-deletion jobs and retry tracking.
-   Evaluate RLS with tenant-isolation tests.
-   Add retention jobs and artifact lifecycle status.
-   Add database backup/restore drills and migration rollback
    procedures.

### Phase 3 --- Scale

-   Partition audit/event tables only when measured volume warrants it.
-   Add read replicas only after read pressure is demonstrated.
-   Consider a dedicated job queue if worker polling is no longer
    appropriate.
-   Keep raw binary artifacts in object storage, not PostgreSQL.
-   Add analytics-specific materialized views only after product metrics
    stabilize.

## 13. Open implementation decisions

Resolve these before the first production migration:

1.  **Authentication provider:** Confirm provider identity format and
    user deletion webhook behavior.
2.  **Repository source:** Git provider integration, uploaded archives,
    or both in the first demo.
3.  **Object storage:** Choose provider, encryption settings, signed URL
    TTL, and lifecycle rules.
4.  **Queue model:** PostgreSQL-backed worker queue versus external
    queue plus transactional outbox.
5.  **Approval policy:** Whether project owners/admins must approve all
    patches or developers may approve their own.
6.  **Retention:** Final artifact, source snapshot, report, and audit
    retention windows.
7.  **Tenant strategy:** Application authorization alone for the
    prototype, or RLS from the first migration.
8.  **Snapshot storage:** Whether source snapshots live in an isolated
    workspace cache or immutable object storage; PostgreSQL stores only
    their metadata.
9.  **Test retries:** Whether to create a new verification run per retry
    (recommended for MVP) or add per-check attempt numbers.
10. **Audit requirements:** Whether IP digests are needed at all; omit
    them if they do not serve a clear security purpose.

## 14. Definition of done

The database implementation is ready for the MVP when:

-   [ ] All schema changes are versioned and reproducible from an empty
    database.
-   [ ] Foreign keys, uniqueness constraints, and check constraints are
    tested.
-   [ ] Workspace membership is enforced for every
    project/investigation/artifact request.
-   [ ] Cross-workspace ID substitution tests fail safely.
-   [ ] Stage retries preserve prior attempts.
-   [ ] Evidence references private object storage and access is
    authorized.
-   [ ] Patch approval is bound to diff digest and base snapshot.
-   [ ] Verification results are derived from actual executed checks.
-   [ ] Terminal investigation outcomes have consistent timestamps.
-   [ ] Secrets are absent from persisted summaries and logs.
-   [ ] Object deletion and retention jobs are idempotent and
    observable.
-   [ ] Migration tests run in CI and backup/restore procedures are
    documented.

## Appendix B --- Example queries

### List recent investigations for a project

``` sql
SELECT id, title, status, severity, current_stage, created_at
FROM investigations
WHERE project_id = :project_id
ORDER BY created_at DESC
LIMIT 50;
```

Run this only after authorizing the caller against the project's
workspace.

### Load the investigation timeline

``` sql
SELECT id, event_type, message, payload, created_at
FROM activity_events
WHERE investigation_id = :investigation_id
ORDER BY created_at ASC;
```

Authorize access through the investigation's project and workspace
first.

### Load latest verification status for a patch

``` sql
SELECT id, phase, status, started_at, finished_at, summary
FROM verification_runs
WHERE patch_id = :patch_id
ORDER BY created_at DESC
LIMIT 1;
```

The UI should also load `verification_checks` for the selected run to
show what was actually executed.

### Find queued investigations for a worker

``` sql
SELECT id
FROM investigations
WHERE status = 'queued'
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT 10;
```

Claim/update the selected rows inside a short transaction. Do not hold
row locks while executing browser sessions or test commands.
